# Database Design Brief — Result Analysis System

**Source of truth:** the Prisma schema at `apps/backend/prisma/schema.prisma` (PostgreSQL provider), the seven SQL migrations under `apps/backend/prisma/migrations/`, and the seed script `apps/backend/prisma/seed.ts`.

**Shape of the database at a glance:** 23 models, 1 enum, 8 explicit join tables / assignment tables, 31 secondary indexes, 14 compound or single unique constraints beyond the primary keys. The design is a permission-first RBAC core, a normalised academic structure (branch → scheme → academic year → semester → subject offering), a fact table for marks, and a supporting layer for file processing, reporting, audit and notifications.

---

## 1. Entity List

### Identity and Access Control
- **User** — A member of the college: staff (administrators, heads of department, teachers, principal) or a student with a provisioned login. Holds the credential hash, activation state, avatar pointer and invitation provenance.
- **Role** — A named bundle of authority (Super Admin, Admin, HOD, Teacher, Principal, Student). A role is nothing more than a label for a set of permissions.
- **Permission** — An atomic ability expressed as a resource plus an action pair, for example "marks" plus "enter_own_subject". Guards check permissions, never role names.
- **UserRole** — Assignment of a role to a user, optionally narrowed to a single branch. The join table between users and roles, and the carrier of branch scoping.
- **RolePermission** — Assignment of a permission to a role. The join table between roles and permissions.
- **RefreshToken** — A hashed long-lived session token with expiry, revocation and rotation (replaced-by) support.
- **PasswordReset** — A one-time password reset request, stored only as a SHA-256 hash of the raw token.
- **Invite** — An invitation to join the system. No account exists until it is accepted, so an unaccepted invite grants no access at all.

### Academic Structure
- **Branch** — A department or engineering branch (CS, ME, CE, EE, ENT). The primary horizontal partition of the data.
- **Scheme** — A curriculum scheme (2019, 2022, 2024) with a JSON rules document describing components and pass thresholds.
- **AcademicYear** — An academic calendar year such as "2024-25", with start and end dates.
- **Batch** — A student cohort, for example "2022-26", tied to the academic year in which the cohort was admitted.
- **Subject** — The identity of a subject: code, name, credits, maximum and passing marks, and the JSON component breakdown. Independent of any branch, semester, scheme or year.
- **SubjectOffering** — A subject's assignment to a class context (branch + semester + scheme). The row that marks and teacher allocations hang off. This is the join that lets one subject be taught to several classes.
- **Examination** — A scheduled examination for one class context, with a status that tracks the result lifecycle from PENDING through PROCESSING to PUBLISHED (or FAILED).
- **ClassTeacherAssignment** — The single class teacher for a class context. The unique constraint enforces at most one per class.
- **TeacherSubject** — Allocation of a teacher to a subject offering for a given academic year.

### Students and Marks
- **Student** — A student record: roll number, name, optional login linkage, branch, semester, scheme, batch and academic year.
- **Mark** — One student's score for one subject offering in one exam type for one academic year. The central fact table of the system.

### File Processing, Reporting, Audit
- **UploadJob** — A trackable file-processing job: what was uploaded, by whom, its status and progress, and the JSON payload extracted from it.
- **Report** — A generated report request: its type, the filters applied, the output file location and its status.
- **AuditLog** — An append-only trail of who did what, to which resource, from which IP address.
- **Notification** — A user-facing message (upload complete, report ready) with read/unread state.

## 3. Relationships

### One-to-many (a parent to many children)
- **User → UserRole, RefreshToken, PasswordReset, AuditLog, Notification, UploadJob, Report, Invite** — a member accumulates roles, sessions, reset requests, audit rows, notifications, uploads, reports and sent invitations.
- **Branch → SubjectOffering, Examination, ClassTeacherAssignment, Student, UserRole, Invite**.
- **Scheme → SubjectOffering, Examination, ClassTeacherAssignment, Student**.
- **Subject → SubjectOffering** — one subject identity taught in many class contexts.
- **SubjectOffering → Mark, TeacherSubject**.
- **AcademicYear → Batch, Student, Mark, TeacherSubject, SubjectOffering, Examination, ClassTeacherAssignment**.
- **Batch → Student**.
- **Student → Mark**.
- **Role → UserRole, RolePermission**.
- **Permission → RolePermission**.
- **User → Student** (optional, one-to-one) — a student record may be linked to a login account.

### One-to-one
- **Student ↔ User**, via the optional `userId` on Student, which is unique. At most one student profile per account and at most one account per student.

### Many-to-many, resolved by explicit join tables
- **User ↔ Role** via the `user_roles` table. The join carries the optional branch scope and grant provenance, so it is a ternary relation in practice: user + role + branch.
- **Role ↔ Permission** via the `role_permissions` table.

### Self-relations
- **Invite → Invite**, via `supersededById`, forming the chain left behind by invitation resends.

### Assignment tables (many-to-many with a year dimension)
- **User (teacher) ↔ SubjectOffering** via `teacher_subjects`, keyed by teacher + offering + academic year. This is the allocation that gates a teacher's right to enter marks for a subject.
- **User (teacher) ↔ class context** via `class_teacher_assignments`, keyed by branch + semester + scheme + academic year with the unique constraint capping it at one teacher.

### Join table names for the ER diagram
`user_roles`, `role_permissions`, `teacher_subjects`, `class_teacher_assignments`, `subject_offerings`, `batches`, and the implicit join of `marks` to `subject_offerings`.

|---|---|---|---|

| | | ACCEPTED | The invitee accepted and an account now exists. |

This is the only declared enum. ## 6. Soft Delete, Audit Trail and Timestamping

**There is no soft delete in the current schema.** No table carries a `deletedAt` column. Deactivation uses boolean `isActive` flags on users, branches, schemes, subjects, subject offerings, academic years, batches and students — a logical deactivation that hides a record from normal reads while keeping its history and all related rows intact. The project guidance to use soft deletes is not yet reflected in the schema.

**The audit trail is a separate, append-only table.** `audit_logs` records the actor, the action, the resource and its identifier, a structured JSON payload, the IP address and the user agent, and a creation timestamp. Rows are written by an interceptor applied only to routes that opt in with an audit decorator, so read paths pay nothing. Two rules govern it: only successful mutations are recorded (a handler that throws changed nothing), and a failed audit write never fails the request — the mutation has already committed, so the failure is logged instead. The write is awaited before the response returns, so a shutdown cannot lose rows.

**The timestamp pattern** is consistent. Every mutable business table carries `createdAt` (defaulted to the database clock) and `updatedAt` (maintained by the client). The larger academic tables — branches, subjects, subject offerings, examinations, class teacher assignments, students, marks, users, invites — additionally carry `createdBy` and `updatedBy` free-text identifiers recording who made the change. These are plain strings rather than foreign keys, so they are not referentially enforced; they are a durable breadcrumb even if the referenced account is later removed. Four tables are deliberately timestamp-light — `academic_years`, `batches`, `role_permissions` and `teacher_subjects` — because they are reference facts rather than mutable business records.

**Token hygiene follows the same principle.** Refresh tokens, password-reset tokens and invitation tokens are all stored as SHA-256 hashes, never in plaintext, so a database leak yields no usable credentials.

## 7. Multi-Tenancy and Scoping

The system is **branch-scoped**, not tenant-scoped in the strict sense: one college, one database, many branches. Three mechanisms combine to enforce this.

**Branch on the role assignment.** The `user_roles` table carries an optional `branchId`. A member whose role assignments all have a null branch is *college-scoped* and sees everything; a member with at least one branch-bearing assignment is *branch-scoped* and every read must be filtered to those branches. A member may hold several roles at once — an HOD who also teaches, for example — so the scope is the union across all their `user_roles` rows. It is therefore read from the database per request rather than embedded in the JWT, because a token carrying one role cannot express the union.

**Branch on the data rows.** Every academic entity carries a `branchId` directly — subject offerings, examinations, class teacher assignments, students. The branch-scoped roles are `HOD`, `PRINCIPAL` and `TEACHER`; Super Admin and Admin are college-wide by default, and student scope is enforced through the student record's own branch plus the optional `read_own` permissions.

**Branch on the join tables.** A teacher-subject allocation, a class teacher assignment and an invitation all carry the branch, so a teacher's permitted subject set is both role-scoped and branch-scoped.

**Scheme and academic year are the other two dimensions.** A class context is the tuple (branch, semester, scheme, academic year), and it is exactly this tuple that the unique constraints on `examinations` and `class_teacher_assignments` protect. Marks carry the academic year directly in addition to the student and the subject offering, so a score is always attributable to a specific year.

**Curriculum year is derived, never stored.** An earlier version stored a `year` column on subject offerings and a `current_year` column on students. Both were removed in the 2026-11-02 migration because the year is a function of the semester, and storing it twice allowed contradictory rows such as "semester 5, year 1" with nothing to reject them. The derivation now lives in a single helper on each side.

## Migration History (for the appendices)

Seven migrations in chronological order: an initial schema creating all tables; the invitation flow and member fields (`must_change_password`, `invited_at`, `invited_by_id`) together with the `InviteStatus` enum; the password-reset table; the invitation supersession chain; the split of `subjects` into a subject identity and a `subject_offerings` assignment table; the user avatar URL; and the removal of the two redundant year columns.

Two deserve a note. The **subject-offering split** (2026-10-25) is the most significant change to the data model. The generated migration would have dropped `subjects.branch_id`, `subjects.scheme_id`, `subjects.semester` and `subjects.year` in the same statement that added the not-null replacement columns, destroying every existing row's data; it was therefore hand-rewritten to be data-preserving — create and backfill `subject_offerings` first, add the new mark and teacher-allocation columns as nullable and backfill them, promote to not-null, then drop the old columns. Legacy marks that collapsed onto the same offering under the new key were deduplicated, keeping the most recent row of each group, and `subjects.code` was made globally unique with deterministic suffixes for legacy duplicates.

The **year-column removal** (2026-11-02) is the clearest expression of the principle that redundant derivable data should not be stored: the curriculum year is derived from the semester by a single helper on each side, so it can never contradict it. The migration repairs any row whose stored year disagreed with its semester before dropping the columns.
